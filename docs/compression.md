# Shrinking what leaves the device

Every attachment is re-encoded on the device before it is written to the offline mirror, so the
blob that sits in IndexedDB, the bytes that cross the wire to R2 and the object billed in the
bucket are all the compressed one. Compression happens inside
[captureDocument](../src/data/capture.ts), which is the single funnel an attachment passes through
on its way to storage, and it runs after the receipt has been read — the parser always sees the
original file, never a re-encoded one.

The entry point is [compressForUpload](../src/lib/compress/index.ts). It returns a blob, a file
name and a content type, and every one of its failure modes returns the original file untouched.
A browser without WebP, a canvas that will not allocate, an encrypted PDF, a decode that throws:
each of those stores the file as it arrived. Compression is never allowed to lose an attachment.

## Images

[image.ts](../src/lib/compress/image.ts) decodes the file to an `ImageBitmap`, draws it to a canvas
and encodes WebP.

- **Transparency survives.** The canvas is never filled with a background, so alpha reaches the
  encoder, and lossy WebP carries an alpha channel. There is deliberately no JPEG fallback: a
  browser that cannot write WebP keeps its original file rather than being handed a format that
  would flatten the transparency onto white.
- **Quality is searched, not chosen.** The encoder runs at the quality floor first. If even that
  overshoots the size budget the result stands, because nothing better is available; otherwise a
  short binary search walks quality up to the highest setting that still fits the budget, so the
  file lands as close under the ceiling as the search resolution allows rather than far below it.
- **Scale is the second lever.** The longest edge is capped before the first encode. If the budget
  is still missed at the quality floor the image is shrunk and re-encoded, down to a floor edge
  past which a receipt stops being legible to a human reading it during a CRA review.
- **The result has to earn its place.** If the WebP is not smaller than what arrived, the original
  is kept. An animated GIF, an APNG, an SVG and an AVIF are all skipped outright — the first two
  because a bitmap decode keeps only the first frame, the third because rasterising a vector is a
  loss with no gain, the fourth because it is already denser than WebP.

## PDFs

[pdf.ts](../src/lib/compress/pdf.ts) uses [pdf-lib](https://pdf-lib.js.org) for writing and the
pdf.js runtime the reader already ships for reading. Two strategies run and the smaller result
wins; if neither beats the original, the original is kept.

- **Restructure.** `pdf-lib` reloads the document and saves it with object streams, which packs the
  cross-reference table and the small indirect objects. It is cheap, it is lossless, and it is
  attempted on every PDF. The gain is structural only — embedded images are copied through
  untouched.
- **Rasterise.** A PDF whose text layer is under 40 characters is a scan, the same test
  [the reader](../src/lib/ocr/pdf.ts) uses to decide whether to run OCR. There is no text to
  protect, so each page is rendered through pdf.js and rebuilt as a JPEG on a page of the original
  point size. This is where a phone-scanned receipt gives up most of its bytes. A document with a
  real text layer never takes this path, so an invoice generated by software stays selectable,
  searchable and sharp.

Rasterising is capped at a page count, because the work is per-page canvas rendering on the main
thread and a long document would cost more than the bytes are worth.

`pdf-lib` is reached only through `await import`, so it lands in its own chunk and no one who never
attaches a PDF pays for it.
